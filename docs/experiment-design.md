# 实验设计：澄清方式与代码实现质量

## 研究目的

ICAE-EVAL 的任务给编码代理一份模糊需求和公开样例，要求它实现可通过未公开测试的代码。本实验研究：**当基础任务、编码模型和公开样例固定时，澄清需求的方式与提问预算如何改变实现质量及开销？** 重点观察外部 Oracle 是否带来增益、主动整理需求缺口的提问策略是否有增益，以及增加提问预算是否总能改善结果。

实验是任务内对照：同一 `realcode@NNN` 的八组使用相同的 Fuzzy L1 任务材料和公开测试样例；D 组按定义使用对应详细需求。每组从干净工作区和新的 Codex 会话开始。组间分数应先在同一任务内比较，再观察跨任务趋势；五个任务不是随机抽样或独立重复试验。

## 八组条件

| 组 | 编码前的需求处理 | 可用外部 Oracle | 预算 | 作用 |
| --- | --- | --- | ---: | --- |
| A | 直接编码 | 无 | 0 | 模糊需求基线 |
| A′3、A′8 | 代理自行识别歧义并作假设 | 无 | 至多 3、8 项 | 区分“额外思考”与外部信息 |
| B3、B8 | 自由选择逐条问题 | 有 | 至多 3、8 次 | 测试一般 Oracle 澄清 |
| C3、C8 | 先列需求缺口、候选问题和优先级，再逐条提问 | 有 | 至多 3、8 次 | 测试有结构的缺口驱动提问 |
| D | 直接阅读详细需求 | 无 | 0 | 详细需求参照条件 |

所有组均有同一套公开样例作为编码脚手架。A′ 的 `actual_questions` 是自行作答的条目数，不是 Oracle 请求。B/C 的一次 Fallback 仍占一次预算。D 不是可直接达到的性能上界：详细需求改变了输入信息量，模型也可能在某个任务上实现失误。

C 的当前策略版本为 `gap_v2_1`。需求代理先枚举可能改变实现的未决缺口，为每个开放缺口提出一个具体候选问题，并给出高、中、低优先级和选择理由；每次答复后更新状态。代理决定问什么，relay 校验请求结构并记录决策，不代替代理判断优先级。B/C 最终传给编码代理的问答由可信 Oracle 服务日志生成，需求阶段末尾的 JSON 摘要仅用于审计。

## 控制与比较

本轮正式数据的编码端均为 `Codex-config`、`gpt-6-sol`、`medium` reasoning；Oracle 为 `Deepseek-V4.1-Flash`，C 的策略版本均为 `gap_v2_1`。比较优先使用同一任务内的差值，例如 B3−A、C3−B3、B8−B3、C8−C3、D−A。这样可以减少不同任务测试数量和难度造成的混淆。跨任务平均仅作为五个任务的描述性汇总。

本实验不能单独识别“更多问题”与“问题质量”的全部因果效应：模型生成具有随机性，每个条件每个任务只保留一个正式结果，且 Oracle 可能 Fallback。后续若要做显著性推断，需要预先固定替换规则和纳入任务，并增加独立重复。
