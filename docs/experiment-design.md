# 实验设计：澄清方式与代码实现质量

## 研究目的

ICAE-EVAL 的任务给编码代理一份模糊需求和公开样例，要求它实现可通过未公开测试的代码。本实验研究：**当基础任务、编码模型和公开样例固定时，澄清需求的方式与提问预算如何改变实现质量及开销？** 重点观察外部 Oracle 是否带来增益、主动整理需求缺口的提问策略是否有增益，以及增加提问预算是否总能改善结果。

实验是任务内对照：同一 `realcode@NNN` 的八组使用相同的 Fuzzy L1 任务材料和公开测试样例；D 组按定义使用对应详细需求。每组从干净工作区和新的 Codex 会话开始。组间分数应先在同一任务内比较，再观察跨任务趋势；五个任务不是随机抽样或独立重复试验。

## 八组条件

| 组 | 编码前的需求处理 | 可用外部 Oracle | 预算 | 作用 |
| --- | --- | --- | ---: | --- |
| A | 直接编码 | 无 | 0 | 模糊需求基线 |
| A′3、A′8 | 代理自行识别歧义并作假设 | 无 | 至多 3、8 项 | 区分“额外思考”与外部信息 |
| B3、B8 | 自由选择逐条问题 | 有 | 至多 3、8 次 | 测试一般 Oracle 澄清 |
| C3、C8 | 先列需求缺口、候选问题和优先级，再逐条提问 | 有 | 至多 3、8 次 | 测试有结构的缺口驱动提问 |
| D | 直接阅读详细需求 | 无 | 0 | 详细需求参照条件 |

## 各组的具体任务与输入

`harness/course_experiment.py` 把需求处理与编码分成独立阶段。需求阶段可读取的本地任务材料仅限本组需求文档和已提供的公开测试样例；B/C 另可通过 relay 请求 Oracle。此阶段不能改动工作区、实现代码，或读取隐藏测试、参考源码及 Oracle 内部材料；程序还会核对工作区在需求阶段前后是否一致。A 和 D 无需澄清，记录为零开销的 `pre_satisfied` 需求阶段。其余组完成需求阶段后，编码从重新初始化的工作区和新 Codex 会话开始。

| 组 | 需求阶段具体要求 | 编码阶段收到的需求文档 |
| --- | --- | --- |
| A | 不运行澄清代理，不生成问答。 | 原始 Fuzzy L1 需求。 |
| A′3、A′8 | 从模糊需求和公开样例中识别重要歧义，分别自行回答至多 3 或 8 项；不得请求 Oracle。最终交付 `questions` JSON，每项标记 `source=agent_assumption`。 | 原始 Fuzzy L1 需求，附加 `Agent assumptions` 小节及自行作答的问答。 |
| B3、B8 | 分别最多向 Oracle 请求 3 或 8 次；每次只问一个具体问题，等完整答复后再决定下一问，不能把互不相关的问题打包以绕过预算。 | 原始 Fuzzy L1 需求，附加 `Oracle replies` 小节及服务日志中成功返回的全部问答。 |
| C3、C8 | 与 B 使用同一 Oracle 和 3/8 次预算，但在每次提问前维护需求缺口、对应候选问题、优先级及选择理由；随答复更新缺口状态。 | 与 B 相同格式的 `Oracle replies`；缺口清单和选择理由保留在轨迹中供审计，不作为额外需求直接交给编码代理。 |
| D | 不运行澄清代理，不请求 Oracle。 | `detailed_prds_oracle/<任务>/start.md` 中的详细需求。 |

### A：直接实现的基线

A 不启动需求澄清代理，`requirements` 记录为 `pre_satisfied`，提问数和澄清耗时为零。编码代理直接读取 Fuzzy L1 的 `start.md` 和预置公开测试样例，根据已有信息实现程序；提示词规定编码阶段不能联系 Oracle。A 保留了模糊需求中的不确定性，用于观察不增加澄清步骤时代理能完成多少要求。后续比较 B/C 与 A 时，差值包含了澄清所得信息和额外推理过程的共同影响。

### A′3：少量自行澄清

A′3 在编码前开启独立需求阶段，要求代理从模糊需求和公开样例中挑选至多三个重要歧义，自己给出答案，且不得请求 Oracle。输出必须是 `questions` JSON；每项都有 `question`、`answer`，并标记 `source=agent_assumption`。如果找不到有用问题，可以返回空列表。程序校验条目数与字段，然后将这些问答写入编码文档的 `Agent assumptions` 小节。编码代理看到的是**未经外部确认的假设**，因此此组检验有限额外推理本身是否有帮助，而不是 Oracle 的信息增益。

### A′8：更多自行澄清

A′8 沿用 A′3 的流程与输出格式，只把自行作答上限提高到八项；仍无 Oracle，也不能读取隐藏测试或参考实现。两个 A′ 组之间改变的是允许形成的假设数量，实际 `actual_questions` 统计的是代理写出的假设条目。更多假设可能补足遗漏，也可能把错误推断写进编码文档，因此预算增加不等于信息更可靠。

### B3：三次自由提问

B3 给需求代理最多三次 Oracle 请求。代理自行决定问什么，但必须一次提交一个具体问题，等待完整答复后再选下一问；不能把无关问题打包来绕过预算。问题若含糊、混合已定义与未定义行为，或超过三个独立主题，Oracle 会整题返回 Fallback，不做部分披露；Fallback 仍消耗一次额度。需求阶段末尾的 JSON 问答只作审计，编码文档中的 `Oracle replies` 由服务日志的原始问答构成，包括成功返回的 Fallback。B3 用于观察少量、无强制缺口清单的外部澄清能带来什么结果。

### B8：八次自由提问

B8 与 B3 使用相同的自由提问规则、Oracle 和编码输入格式，最多可请求八次。代理可以在收到答复后继续追问、换角度提问，或停止；每次 Fallback 同样占一个名额。实验关注额外预算能否触达更多可回答的需求约束，同时也记录实际提问数、约束覆盖率和 Fallback。B8 与 B3 的区别是预算上限，不能把八次预算直接等同于八条有效新信息。

### C3：三次缺口驱动提问

C3 使用与 B3 相同的三次 Oracle 预算，但需求提示词要求在第一次提问前梳理所有会影响实现的未决缺口。每个开放缺口都要有稳定 ID、主题、不确定性及一个对应的具体候选问题；候选问题标明高、中、低优先级和理由。每次请求都提交当前完整缺口清单、候选问题和本次选择理由；relay 校验结构与所选问题的一致性，代理自己决定取舍。答复后须更新缺口状态，只有得到答复或公开证据支持时才标记已解决。编码代理只收到服务日志中的 `Oracle replies`，不会把缺口清单当作额外需求。C3 用于与 B3 比较：在相同预算下，结构化识别与排序问题能否改善澄清效果。

### C8：八次缺口驱动提问

C8 沿用 C3 的 `gap_v2_1` 缺口清单、逐次更新和请求校验规则，预算提高到八次。提示词要求将可能产生不同结果的操作或边界场景分成不同缺口；临近预算用尽时，重新检查尚未解决的高、中优先级缺口，并权衡实现影响、预期价值和 Oracle 是否可能回答。宽泛提问得到 Fallback 后可考虑缩小问题，已足够具体却仍未获答复时通常暂缓该缺口。C8 既可与 C3 比较预算影响，也可与 B8 比较同为八次预算时的提问组织方式。

### D：详细需求参照

D 不运行需求澄清代理，也不联系 Oracle，直接将 `detailed_prds_oracle/<任务>/start.md` 交给编码代理。它使用与其他组相同的公开测试样例和编码执行流程，但输入由模糊需求改为预先准备的详细需求。D 用于参照需求信息更充分时的实现表现；一次生成的代码仍可能有实现错误，所以 D 不保证取得最高分。
