# 实验设计：澄清方式与代码实现质量

## 研究目的

ICAE-EVAL 的任务给编码代理一份模糊需求和公开样例，要求它实现可通过未公开测试的代码。本实验研究：**当基础任务、编码模型和公开样例固定时，澄清需求的方式与提问预算如何改变实现质量及开销？** 重点观察外部 Oracle 是否带来增益、主动整理需求缺口的提问策略是否有增益，以及增加提问预算是否总能改善结果。

实验是任务内对照：同一 `realcode@NNN` 的八组使用相同的 Fuzzy L1 任务材料和公开测试样例；D 组按定义使用对应详细需求。每组从干净工作区和新的 Codex 会话开始。组间分数应先在同一任务内比较，再观察跨任务趋势；五个任务不是随机抽样或独立重复试验。

## 八组条件

| 组 | 编码前的需求处理 | 可用外部 Oracle | 预算 | 作用 |
| --- | --- | --- | ---: | --- |
| A | 直接编码 | 无 | 0 | 模糊需求基线 |
| A′3、A′8 | 代理自行识别歧义并作假设 | 无 | 至多 3、8 项 | 区分“额外思考”与外部信息 |
| B3、B8 | 自由选择逐条问题 | 有 | 至多 3、8 次 | 测试一般 Oracle 澄清 |
| C3、C8 | 先列需求缺口、候选问题和优先级，再逐条提问 | 有 | 至多 3、8 次 | 测试有结构的缺口驱动提问 |
| D | 直接阅读详细需求 | 无 | 0 | 详细需求参照条件 |

## 各组的具体任务与输入

`harness/course_experiment.py` 把需求处理与编码分成独立阶段。需求阶段可读取的本地任务材料仅限本组需求文档和已提供的公开测试样例；B/C 另可通过 relay 请求 Oracle。此阶段不能改动工作区、实现代码，或读取隐藏测试、参考源码及 Oracle 内部材料；程序还会核对工作区在需求阶段前后是否一致。A 和 D 无需澄清，记录为零开销的 `pre_satisfied` 需求阶段。其余组完成需求阶段后，编码从重新初始化的工作区和新 Codex 会话开始。

| 组 | 需求阶段具体要求 | 编码阶段收到的需求文档 |
| --- | --- | --- |
| A | 不运行澄清代理，不生成问答。 | 原始 Fuzzy L1 需求。 |
| A′3、A′8 | 从模糊需求和公开样例中识别重要歧义，分别自行回答至多 3 或 8 项；不得请求 Oracle。最终交付 `questions` JSON，每项标记 `source=agent_assumption`。 | 原始 Fuzzy L1 需求，附加 `Agent assumptions` 小节及自行作答的问答。 |
| B3、B8 | 分别最多向 Oracle 请求 3 或 8 次；每次只问一个具体问题，等完整答复后再决定下一问，不能把互不相关的问题打包以绕过预算。 | 原始 Fuzzy L1 需求，附加 `Oracle replies` 小节及服务日志中成功返回的全部问答。 |
| C3、C8 | 与 B 使用同一 Oracle 和 3/8 次预算，但在每次提问前维护需求缺口、对应候选问题、优先级及选择理由；随答复更新缺口状态。 | 与 B 相同格式的 `Oracle replies`；缺口清单和选择理由保留在轨迹中供审计，不作为额外需求直接交给编码代理。 |
| D | 不运行澄清代理，不请求 Oracle。 | `detailed_prds_oracle/<任务>/start.md` 中的详细需求。 |

### A：不做需求澄清

A 组直接依据模糊需求和公开样例完成实现，不安排额外的需求分析，也不向 Oracle 提问。它保留了任务原有的不确定性，提供一个判断其他澄清方法是否带来变化的起点。A 组的表现也提醒我们：代理即使没有获得新信息，仍可能凭已有描述和样例推断出部分未明确写出的要求。

### A′3 与 A′8：自行提出并回答问题

这两组在动手实现前，先让代理找出它认为最重要的需求歧义，并根据已有需求和公开样例自行给出答案。A′3 最多处理三个问题，A′8 最多处理八个；如果没有值得澄清的问题，可以少于上限。形成的回答会供后续实现参考，但没有经过 Oracle 确认，因此只是代理的判断，可能正确，也可能把错误假设带入实现。

设置 A′ 组，是为了观察**单纯增加需求思考**能否改善结果。将它们与 A 比较，可以看到增加分析步骤后的变化；再与相同预算的 B、C 组比较，有助于讨论外部回答相对于自行推断的价值。不过，A′ 的预算限制自行形成的假设数，B/C 的预算限制向 Oracle 提问的次数；相同数字并不意味着各组获得了同等数量或可靠性的信息。A′3 与 A′8 之间只改变允许处理的问题数量，因此也能观察更大的自我澄清预算是否有用。

### B3 与 B8：自由选择问题并询问 Oracle

B 组允许代理就模糊需求中不确定的行为向 Oracle 求证。代理自行决定问题的主题和顺序，每次根据已经获得的答复决定是否继续追问。B3 最多问三次，B8 最多问八次；这两个上限使实验能分别观察有限预算和较宽预算下的自由提问效果。

Oracle 只对具体且在其掌握的需求范围内的问题给出信息。问题过于笼统、混合了已知与未知的行为，或包含过多互不相关的主题时，可能得到不披露额外要求的统一回复；这仍占用一次提问机会。实现阶段获得的是 Oracle 实际给出的回答，包括这种未能提供新信息的回复。B 组因而考察的是**代理能否通过自行选题获得有用的外部澄清**，而不只是可用提问次数的多少。

### C3 与 C8：先整理需求缺口，再询问 Oracle

C 组同样可以向 Oracle 提问，三次和八次的预算分别对应 C3、C8。它与 B 组的区别在于选择问题的方法：代理先系统梳理需求与公开样例中尚不确定、且可能影响实现的事项，为每个事项准备具体问题，并判断其重要性与可回答性；得到答复后，再更新尚未解决的事项，决定下一次问什么。对于可能产生不同结果的操作或边界情形，要求分别考虑，以免一个宽泛问题掩盖关键差异。

这种设计希望把有限提问机会优先用于实现影响较大的缺口，并减少重复、模糊或难以回答的问题。C3 与 B3、C8 与 B8 使用相同的外部信息来源和对应预算，因此它们的比较重点是**提问组织方式**。C3 与 C8 的比较则关注：在采用同一种缺口驱动策略时，额外预算能否帮助代理解决更多重要的不确定性。缺口清单只用于决定如何提问；后续实现依据的是实际获得的 Oracle 回答。

### D：直接提供详细需求

D 组所用的详细需求，是将该任务的原始模糊需求与隐藏需求合并后形成的。代理从一开始就能阅读这份较完整的需求说明，无需通过提问逐步获取信息。设置 D 组，是为了观察需求被充分说明时的实现表现，并为其他组提供参照。由于它获得的需求内容与其他组不同，D 的结果适合用于对照，不应被当作其他组必须达到的分数。
